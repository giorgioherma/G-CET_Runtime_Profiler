## Cross-mod implementation design

1. **Input-woken UI/features:** Retain mod-owned `registerInput`/`registerHotkey`, never duplicate or hardcode. Sleep heavy update/draw, native lookup and allocations when feature is hidden/inactive.
2. **Event-woken features:** Keep `Observe`/game lifecycle listeners and event-trigger queue draining. Expensive work executes only after the authored event; native registration count may not fall.
3. **Proximity-woken features:** Reuse fixed location data where proven immutable; retain cheap discovery (potentially slower) so approach triggers still work. Never freeze other mods' dynamically registered locations.
4. **Quest-woken features:** Separate installed journal entry, discovered mission, actual active quest, completion and cooldown; trigger on authored state transitions, not mere journal presence.
5. **Realtime controls:** Keep observer ordering, consumption and input delivery for live flight, camera, movement, racing, physics and minigames.
6. **Version fluidity:** Accept pristine, partial and complete stages; prove each unchanged stage by source, fail closed on author control-flow changes rather than broadening regex matching.
7. **Testing:** Per-mod original/live/partial fixtures, dormant wake, queued work, resume, in-game controls, and measured allocations/callbacks before declaring runtime savings.

## Boundaries

The explicit user SKIP list remains authoritative. The table above resolves the previously unknowns to actionable families; it does **not** authorize arbitrary source rewriting or prove that all 62 mod rules have been optimized. Main branch is outside scope.
