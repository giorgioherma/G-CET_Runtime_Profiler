Native operations must not be owned by the temporary Profiler ASI, which restores the official CET binary afterward.

**Earlier proposals below are historical where they conflict with this decision.** In particular, `init.lua` + `threshold.lua` as a complete controller is superseded, and 5–8 natural cycles or exact time-to-trigger must not be a prerequisite for a pressure/headroom-first experiment.

## Purpose and non-goals

The objective is **preventing avoidable frame stalls caused by accumulated LuaJIT garbage/heap pressure**, with the least practical runtime overhead. The primary control signal is **live heap pressure and predicted time remaining until the natural LuaJIT collection-trigger region**. Collector and CapFrameX evidence establish a *latency budget* for safe assistance; they do **not** mandate constant higher GC effort.

Upstream source optimizations (eliminating pointless allocations, duplicate work and excessive Lua→native polling, dormancy, caching) remain the first line of defense. The controller is a small **incremental helper**, not a substitute for fixing data producers, not a replacement collector, not a forced full-GC scheduler and not Choom Memory Booster. Do not introduce aggressive global collection, synchronous full collections or high-frequency monitoring that itself worsens frame pacing.

## Installation, data ownership and configuration — approved

- G-GC is **shipped with the G-CET Updater and generated/configured by Resolver** for the user's installation. It is independent of Choom Memory Booster; CMB is deliberately removed from the live test and source baseline.
- Proposed source/generated Lua layout: `bin/x64/plugins/cyber_engine_tweaks/mods/G-GC/init.lua` and `threshold.lua`, or an equivalent correctly owned packaged layout proven during implementation. A single controller owns the incremental assistance; do not duplicate GC helpers inside individual optimized mods.
- A **Profiler + CapFrameX capture determines the user's actual frametime stall/hitch budget**. Resolver derives the configured threshold from the latest admitted capture and **overwrites the exact configuration value on every generation**. No historic thresholds, historical config database, hardware benchmark or hardware detection pass is required.
- The earlier design proposed a conservative calibration formula `hitch_threshold_ms = max(25 ms, 1.5 × median CapFrameX frametime)` (a prior example produced 25.2045 ms). Treat this as the *design-era proposal to verify against the currently admitted profiler hitch semantics*, **not** as proof that a particular hardcoded 25 ms threshold is universally valid or that a shipped generator exists. The latest authoritative threshold must come from the actual Profiler/Resolver evidence; distinguish ordinary P95/P99 frametime reporting from the stall boundary selected for control.
- **Runtime must not poll CapFrameX, scan hardware, replay profiler logs, maintain a historical capture database or infer the user’s hardware.** Its only runtime job is lightweight heap/collector observation and assistance informed by the generated scalar configuration. Missing or invalid profile evidence must be reported, not silently replaced with fabricated calibration.

## Runtime decision model — approved direction

1. **Observe very cheaply.** Use bounded/low-frequency observations of the current LuaJIT heap, changes over elapsed time, and the collection-cycle progress or observed natural trigger regions that can be read safely from the supported LuaJIT/CET environment. Avoid per-frame allocations, busy waits, repeated expensive native getters and unbounded history.
2. **Characterize unassisted natural disposal.** Learn where LuaJIT naturally begins collecting from a rolling median over approximately **5–8 valid natural cycles**. The trigger region is an empirical, adaptive heap observation, not a universal fixed-MiB limit. **Do not train this baseline on forced or controller-assisted cycles** and do not equate a heap drop with provenance or reclaimed garbage from any specific mod. When too few valid cycles exist, use a conservative, explicitly uncalibrated state.
3. **Estimate pressure from live growth.** Compute a bounded/smoothed *recent net heap growth rate* from observations, separate from the Profiler's **cumulative positive allocator bytes**. Rising gameplay load accelerates it; idle/light gameplay should lower or flatten it. If growth is flat/negative, no predicted near-term pressure is asserted. Forecast, when meaningful:
   `time_to_pressure ≈ max(0, learned_natural_trigger_heap − current_heap) / max(recent_positive_net_heap_growth_rate, epsilon)`.
   The controller should never interpret positive allocation request totals as retained/live-heap growth.
4. **Adapt incremental assistance only when it matters.** Maintain a very light baseline/maintenance mode; increase bounded incremental assistance progressively as remaining time shrinks, heap grows toward the learned trigger region, and predicted risk approaches the configured latency safety margin. Reduce assistance when pressure eases. Require conservative maximum effort, hysteresis/cooldown, and no execution storm. The exact safe helper primitive, time slicing, cadence and intensity bounds must be validated **before implementation is considered ready**; do not invent a `collectgarbage` API guarantee from this design.
5. **Minimize visible latency, preserve LuaJIT safety.** Respect ordinary collector progress, session/loading transitions, explicit user/game lifecycle and fallback behavior. Do not claim a helper can interrupt a single long indivisible atomic/sweepstring/finalize step; aim to reduce the likelihood/backlog of large natural stalls, then verify empirically. Fall back to ordinary LuaJIT behavior if the controller cannot establish safe heap/collector state.
6. **Use evidence to retune, not heavyweight runtime profiling.** Later Resolver runs may regenerate a new exact threshold from better captures. No permanent in-game detailed allocation profiler is required merely to dispatch the lightweight helper.

**Important distinction:** the generated **frametime latency threshold** is not the same variable as the **learned natural GC heap-trigger region**. The first bounds acceptable *visible stall cost*; the second plus *recent growth rate* predicts *when heap pressure will become urgent*. Assistance responds to the second while respecting the first.

Thus the deployed controller was present but its pressure gate could not allow assistance. The heap slope staying similar at 0 vs 100 is unsurprising in that condition; the absence of explicit calls/marks does not alone prove what sliders the user touched outside the capture.

**Authoritative repair:** `GgcControllerSource` now generates the same single owned runtime with **live pressure-band adaptation**. During low-rate `collectgarbage("count")` observations, it tracks the live peak and detects a significant natural heap drop. One drop episode learns an approximate current-stack pressure region; consecutive collection-drop samples are coalesced with an eight-second cooldown. Events occurring within ten seconds of a controller-assisted step are excluded from learning, avoiding training the prior on assisted cycles. Until a clean drop is observed, the capture's pressure region remains a conservative prior; assistance is disabled below it. After an observed unassisted cycle, the current heap and smoothed net growth drive requested work, **not** a hard-coded stock-stack heap reference. The original captured **frametime tolerance, reserved gameplay headroom and CPU allowance remain hard limits**; neither learned heap pressure nor a 100% slider can override them. Request sizes are bounded to 1–128 KiB incremental work per attempt (not guaranteed wall milliseconds), and natural drop episodes suspend assistance.

**Real control diagnostics:** The CET overlay now renders the actually applied intensity/frequency, captured prior versus live learned pressure reference, current heap/pressure/growth, active suppression reason, requested incremental work size, step/cycle/failed counts and provisional step CPU cost. Periodic/setting-change `GGC_V2` Profiler markers identify actual settings during capture; 100% increases permitted request size while 0% unconditionally disables assistance. A separate 250–5000ms frequency slider determines minimum attempt spacing, independent of heap observation cadence. Note: even functioning incremental work need not reduce **positive allocation rate or instantaneous rising heap slope**; validate actual step counts, collector phase times and severe frametime tails.

**Previously generated installs:** The authoritative runtime generator recognizes the exact inert historical V1 generated source via an embedded **source-equivalence migration reference**, without accepting arbitrary marker-bearing edited Lua or requiring manual deletion. The archived V1 text is never executed as a second controller; the new generator owns output and overwrite. A permanent regression simulates an October stock calibration against a November-like lower live heap, verifies pressure learning, 0 vs 100 step counts/sizes and heavy-frame/load fail-closed behavior, and tests the deployed V1 → current source-equivalent upgrade and unsafe drift refusal.

## November 3 correction — capture allowance, live heap demand

**User-approved interpretation:** Live heap pressure is the controller's PRIMARY demand input, not an "adaptive fallback". The currently selected Profiler/CapFrameX capture determines the player's allowed assistance ceiling **before generation**: measured median frametime, hitch tolerance, a substantial headroom reserve and a provisional modest collection CPU allowance. Resolver also selects **nonzero starting intensity and frequency** when there is measured spare margin; it does not default qualified captures to observe-only and require a user to enable assistance manually.

The runtime continuously scales actual incremental-step effort from the **observed live heap position and growth** inside the approximate capture-derived pressure band; when low, it does not request assistance. The generated intensity controls the maximum requested step size, and frequency the minimum permitted separation. Manual CET sliders adjust these ceilings during the session, subject to the capture-derived headroom/CPU guard. Under heavy gameplay or absent usable margin, assistance backs off. Low-headroom captures may deliberately start at 0% because no safe allowance was established.

The first **provisional** allowance formula for A/B is: `frameRoom = hitchTolerance − medianFrame`, `reserve = max(4 ms, 0.60 × frameRoom)`, `usable = max(0, frameRoom − reserve)`; default intensity is `round(20 + 25 × min(1, usable / (0.20 × hitchTolerance)))`%, and default minimum step interval is `50 × round((1700 − 700 × min(1, usable / (0.20 × hitchTolerance))) / 50)` ms, only if `usable > 0`. The one-second CPU allowance is `clamp(0.12 × frameRoom, 0.15, 2.0)` ms/s if usable, otherwise zero. These coefficients are **experimental starting points, not measured safe GC-step times**. The user will calibrate against real gameplay. The capture's heap snapshots still describe only a rough pressure region, not precise natural GC triggers.

**Validation of this calibration correction:** [CI #41561296779](https://github.com/giorgioherma/G-CET_Runtime_Profiler/actions/runs/41561296779), code `c73e77ee5c7e871c6c35f89a4169b1541c61c09a`, **SUCCESS 6/6**, both v1.3.4 packages built (Resolver ID 13197063631 / Profiler ID 13196873974). The permanent calibration test validates the nonzero recommended defaults, capture-to-capture changes and zero-headroom case; the mocked Lua contract validates automatic pressure-gated work before player overrides. No actual game frametime or native step wall-time acceptance is implied.

**Important remaining architecture gap:** The currently CI-tested runtime is an experimental Resolver-generated CET Lua worker, **not** the independent persistent native-owned collector required by the earlier user-approved design. Do not mistake this calibration correction or green CI for completion of that native runtime/Updater requirement, measured wall-clock safety, or gameplay acceptance.

## November 3 implementation — source integration, not gameplay acceptance

- The **existing** `GgcCaptureCalibrationService.Build` interprets only the currently selected `CET_Resolver_Input.json` during Resolver ANALYZE, writing `gGcCaptureCalibration` into `G-CET_Resolver.json`. GENERATE consumes **that same already-interpreted record**; it does not independently re-read or re-infer a separate heap trigger. Missing measured hitch/heap evidence is reported, never replaced by fixed thresholds.
- `GgcControllerSource.TryStage` composes **one** dedicated `G-GC/init.lua` and `G-GC/threshold.lua` into the authoritative Resolver overlay ZIP. No executable standalone ZIP should be installed. Generation is offered even when no ordinary mod transform remains. The G-GC-owned callback is excluded from generic mod rewriting; an unknown/modified third-party `G-GC` source is refused. New valid captures replace old recognized calibration directly; identical capture generation is idempotent.
- Captured **median frametime and hitch tolerance** are separate from the runtime reserve. Observed **slow collector-operation heap snapshots** provide only an approximate pressure region (median, P25/P75, broad slack). They are NOT necessarily cycle entry points, and do not establish collector timing, retained-object provenance or system RAM. There is no user RAM override because the Resolver handoff does not actually measure installed RAM.
- The runtime checks heap every **0.75 seconds**, not every frame, and uses a compact rolling growth signal. It requires observed pressure, sufficient headroom, valid game world and permission from the current interval/budget before attempting any `collectgarbage("step", n)`. It does **not** request `collectgarbage("collect")`, override LuaJIT GC parameters, start a native thread or install additional mod-specific workers.
- CET overlay sliders set **intensity 0–100%** and independent **minimum step interval 250–5000 ms** during the same game session. Zero intensity is a manual observe-only setting (or an automatic no-headroom safety result); qualified captures with spare margin now receive capture-derived nonzero starting settings. A new Resolver pass rewrites the calibrated threshold file; UI slider changes are in-session experimental overrides. Bounded setting-change Profiler markers support multi-setting comparisons in the same capture.
- **Cost safety is provisional.** The generated `maxAssistCpuMsPerSecond` is a deliberately small share of the observed tolerance-minus-median, and `frameReserveMs` preserves most of the available margin. The runtime uses an EMA of CET frame delta for backoff and `os.clock()` for an approximate step **CPU** duration; neither provides hard real-world GC phase preemption or an exact elapsed wall-clock budget. Real native GC phase timing plus CapFrameX must establish the actual cost before permitting an assisted default or declaring production readiness.
- Permanent calibration/generation/overwrite/drift tests live in `tests/GgcCaptureCalibrationContract`; mocked real-source Lua tests in `tests/GgcRuntimeLuaContract.lua`, wired into main CI. [Main CI #41559043632](https://github.com/giorgioherma/G-CET_Runtime_Profiler/actions/runs/41559043632) **SUCCESS 6/6** at implementation SHA `8fb2159659cc78e910bc333bcab86c33f2986cc0`, both portable products packaged at version 1.3.4 (not bumped). Its fixed private original-source run did **not** exercise a current G-GC-admitted capture, so the new G-GC generator itself is separately contract-tested; the user's current-capture complete overlay still needs verification. **Green CI is only a build/contract result; user-controlled same-save runtime A/B and world-load tests remain required.**

## Acceptance and implementation gates

- **Do not start implementation solely by applying a 25 ms scalar or by forcing more collection.** First characterize collector trigger/disposal behavior and time-binned heap pressure across light and combat intervals using the existing measurements, distinguishing observed natural cycles, sampling gaps and controls.
- Specify one authoritative lightweight G-GC owner and its runtime API/capabilities; no Choom dependency, no duplicate ownership with 0-Engine, and no dynamic per-mod semantic GC scheduler.
- Test idle/low pressure (no boost), sustained combat/high pressure (bounded predictive assist), transitions/loading, burst allocations, controller disabled/unavailable fallback, long natural GC steps, repeated sessions and failure of trigger estimation. A continuous baseline probe must demonstrably cost very little.
- Evaluate **whole-game** frametimes/CapFrameX episodes and catastrophic stalls, LuaJIT heap trajectory, collector step/phase timing, CPU overhead, allocation rates and gameplay correctness against repeatable same-save/same-route unassisted control. Improvements are hypotheses until measured; excessive controller CPU, altered gameplay timing, memory retention, or changed GC safety are blockers.
- Keep upstream source optimization opportunities distinct: review top allocated-byte/ops/birth owners, identify **unnecessary** production using actual author source and lifetime/escape proof, then repair authoritative generators only. Legitimate large allocations are not automatically defects.
- Follow G-CET fixed stage order, original→partial→idempotent/unsafe drift tests, framework/native dependency checks and CI. **This is documentation only; no controller generated code, product bump or gameplay validation has been completed.**
